# Phase 1 security boundary

Supabase Auth verifies identity through server-side getUser, never a browser role or an unverified session claim. UserProfile.active, persisted RoleMembership and explicit UserScope determine application permissions. Anonymous, unprovisioned and disabled users cannot access records. API handlers repeat authorization independently of the page/layout. Request IDs are server generated.

PostgreSQL is accessed only by server-only Prisma modules. The DATABASE_URL connection role is the application service boundary; ORM queries do NOT automatically inherit a Supabase user's RLS identity. There are no browser database queries. Bootstrap/migrations use an operator-controlled database connection; use a distinct restricted runtime role in production. Grant only SELECT/INSERT/UPDATE on masters, access SELECT, audit INSERT/SELECT, outbox INSERT/SELECT, idempotency INSERT/SELECT and required sequence privileges. Do not give the runtime role schema ownership, BYPASSRLS, migration or audit-trigger alteration privileges. Explicit scope predicates are mandatory for every read.

Writes check exact APP_URL Origin, JSON size/type, authenticated identity, active ADMIN membership again inside the transaction, input schema, parent relationships and version. Serializable transactions and transaction-scoped advisory locks serialize actor/idempotency-key retries. Same key/different payload is a conflict. Record, immutable audit and outbox are committed atomically. Idempotency responses are retained (no unsafe time-based eviction implemented). No network call occurs within these master transactions.

Native managed auth cookies refresh through Next proxy. Auth route handlers set cookies through Supabase SSR. Password login/recovery calls use provider limits and generic errors. Production must enable managed anti-abuse/CAPTCHA/MFA as required by the owner; custom internet-scale rate limiting is not implemented. Use HTTPS and approved Supabase redirect allowlists; disable provider public signup. No fake login, localStorage database, seeded password or auth-bypass endpoint exists.

Initial ADMIN bootstrap is a CLI with a database advisory lock, requires an existing verified identity access token and refuses once any ADMIN membership exists. Additional invited identities may be provisioned by an operator running provision-user with a server-only Supabase admin key and an active administrator reference. Anyone able to run this CLI with database/admin credentials is in the trusted operator boundary; it is not a web authorization shortcut. No public user-role editing endpoint is exposed.

Private file evidence, storage policies, malware scanning, assignment checks for task resources, outbox dispatch and OTP are not implemented until their workflow phase. No public bucket is created. Production and Supabase integration are unverified without credentials.

The initial migration explicitly revokes table privileges from PUBLIC and Supabase anon/authenticated roles when those roles exist. Browser publishable keys cannot be used as a direct alternative path into the master tables. This complements server authorization; it does not assert that Prisma inherits end-user RLS. Use a dedicated runtime role and verify grants in staging.
